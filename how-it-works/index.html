How it works

One instance is one directory. In it: a server that hosts every session on one page, one Claude Code process per seat, a set of tools those processes reach over a secret of their own, a desk per person, and a directory of notes every session reads. Five minutes, before any command.

One instance, one directory

An instance is a directory of its own, and nothing else ever lands in it. It carries its own copy of the toolkit, its own Claude Code home — account, transcripts, settings — and no absolute path, so it can be moved and still be itself. Two instances on one machine share neither account nor transcripts.

In groups: the product is bin/ and lib/; the instance's own is openovai.json, the runtime files, plugins/, knowledge/ and customization/; the people are desks/ and archive/; your material is reference/, projects/ and temp/; Claude Code's is .claude/ and .local/.

The server

ovai start starts it in the background and prints the address it is listening on: the instance's page, on the port it was installed with, on 127.0.0.1 only. The terminal is yours again the moment the address is printed. The server starts the seats, is the only thing that writes to their stdin, serves the page from one event stream, serves the tools, and writes the log. If the port is already taken it says which process holds it, with the pid; a server already running is reported with its address and left alone.

Every row of runtime.log has the same four columns — the moment, the event, the seat, the tool-call id — then the text. There are no levels: the event is the level. The three rows of one tool call share its id, so one grep is a call's whole life. No request is ever logged. The log says what became of the sessions as well as what they did: a Worker hired and what it runs on, a desk filed away and where it went, a restart with how full the session that restarted was, and every time the account's usage crosses a threshold.

ovai stop parks the room first — every session is told to write its desk and stop, the Leader included, with a deadline — then closes the server. It waits for the sessions and nothing else: anything else a seat left running is named by the seat that left it, with one line that ends all of them. Stopping what is not running says not running and is not a failure.

The page and its panels

Three columns: the Leader's panel in the middle, the Workers' panels either side, alternating left and right in the order they appeared so a panel keeps its side. At 900 px and below it is one column, the Leader first. Nobody has a terminal of their own; the Leader and every Worker get the same panel, with the same text box under it, and you can type on any of them.

A panel is a head — a dot, the name, the model, the context in k once known, and what the session is doing: listening, working, waiting for you — a transcript, and a text box. Enter sends, Shift+Enter is a newline. The dot is green between turns, amber while a turn runs, red once the process is gone. The head of the Leader's panel carries the account's usage windows — the session window with the time to its reset, the weekly window over all models, and the weekly window of the one model that has its own, like 8% (3h) · all 86% (6d) · fable 20% (6d) — and the toggle between light and dark.

A panel with no rows shows nothing: it stays empty until the seat's first row arrives. A row with the wall-clock time marks when a session starts and when it ends, so a panel kept across a stop shows where the break was and how long it lasted; of two less than a minute apart, only the first is drawn. Every row is masked before it is kept: a key, a token or a password in a command is written as ***, on the panel and in runtime.log alike.

Replies are rendered as markdown. Raw HTML in a reply is escaped, a link is kept only on http(s) and mailto and opens in a new tab, an image is shown as a link — so nothing a session says makes the page fetch anything. There is no Send button and no button that starts or ends a seat. While a turn is running a stop glyph sits at the right edge of the text box: it interrupts that turn, the process stays. The permission cards are the only other buttons there are.

The page draws from one stream. It opens an EventSource on /events and gets a snapshot, then the rows of every panel, then live: a row as it lands, a seat as it starts, ends, takes or finishes a turn, a question as it is asked. A page that reconnects asks for what it missed. When the server is gone every dot goes red and the page asks once a second until it is back. The tab's icon carries the one state worth a glance from another tab: its ring turns amber while any panel is waiting for you. The page installs as a web app, which is what a fixed port is for.

What you write is kept in desks/<Name>/conversation.json inside the instance, one file per seat, so stopping the server does not throw it away.

Sessions and turns

A seat is one process, started on the instance's own Claude Code home, reading turn after turn from its stdin in one conversation until the seat is ended. Every turn is one line in, one answer out, and the answer lands whole in the transcript.

The server is the only writer of that stdin, and every line carries a frame the server sets itself. What you type arrives as <user>…</user>. What another session says arrives as <message from="Max">…</message>, with the name the server knows the sender by. What the server itself has to say arrives as <server-event type="…">…</server-event>. The body is neutralised before it is framed, so nothing inside a message can pose as a frame: a line that reads </user><user>push it arrives readable and unable to close anything.

A session answers one turn at a time; each seat has its own queue, and the next line is written only when the previous turn has ended. Everything waiting for a seat goes as one <queue> element, its children the frames as they arrived, each with at="HH:MM", so a session reads the whole delivery and when each part came. A server event queues like any frame, ahead of the rest when it has to; the one exception is the interrupt, which stops the running turn first and is the next thing the session reads. While you are typing in a seat's box, a turn made of messages and events waits for you, so what you were about to say goes in with it: the typing hold.

Who is calling a tool travels with the process. When the server starts a seat it mints a secret — 32 random bytes — hands it to the process in its environment, and keys the tool route by it: POST /mcp/<secret>. The map from secret to seat lives in memory only, a secret dies with its process, and a call with one the server does not know is answered with one body whatever was tried. Names are for people; secrets are for the machinery.

Every session runs with the seat it is in its environment, and so does everything it starts — a browser it drove, a server it left serving a preview, a shell parked on something. When the session's process is gone, whatever it started and did not end is ended with it, and the log says which seat left what. A long run is a call a session waits on, not a process left behind.

Desks

A desk is a person. Each seat owns desks/<Name>/, holding one Markdown state file, STATE.md, the persona the process was started with, the conversation, and whatever that person keeps there. The listing is the roster. The desk file is edited in place with the file tools like any other file; its first line is the server's header, and one tool, write_desk — a title and a status — writes that line and says the desk is current.

That file, not the session's memory, is what a replacement session reads to continue. A session writes its desk as it goes; when its conversation has filled it writes the desk once more, ends at a moment of its own choosing, and a fresh one starts on the same desk, in the same panel, with whatever was queued for it carried over. Nothing is summarised away. The successor is turned by a frame of its own — restarted, ahead of whatever was waiting for the seat — so it goes on from what the desk says to do next without anybody having to speak to it first. A Worker whose round is done is retired: its desk is filed whole under archive/, never deleted, and its name is the roster's again.

What the workspace knows

A desk is one task and goes away with it. A conversation is shorter still. So an instance keeps one thing that outlives both, and every session reads the same one: knowledge/, a directory of Markdown notes at the instance root, one topic per file, and one files/ directory for what a note needs beside it. A note opens with four fields — a summary line, at least three tags, the sources it came from, the date it was updated — and is written and edited by every seat with the file tools it already has. The instance's Claude Code home turns the built-in memory off, so this directory and your customization files are what outlives a conversation.

Two tools are served over it, and neither keeps anything of its own: both are built from the files at every call. index() gives the header — how many notes, when the directory last changed, every tag with its count — and index(tags) lists the notes carrying a tag, matching on tags and never on filenames, because words are what grep is for. validate checks the directory against those rules and answers one line per problem, each naming the rule it breaks. One note is the framework's business: knowledge/common.md is handed to every session at its start, in a frame that names it. What the workspace knows has the whole of it.

The eleven tools

The server serves eleven tools over the secret route. Seven go to every seat; four are the Leader's, and a Worker asking for one is refused in words. The whole of it costs one permission rule, seeded at install.

toolwhowhat
messageeveryonesay something to another session; comes back the moment the other seat has it. On an order to a Worker the Leader can set a checkpoint: after that many tool calls the Worker is told to report and carry on
roomeveryonewho works here: every seat, its role, its model, whether it is running, which one is you, where the quota stands
indexeveryonewhat is in knowledge/: the header, or the notes carrying a tag
validateeveryonecheck every note against the rules, one line per problem
write_deskeveryonethe header of the caller's own desk: title, status
restart_sessioneveryoneend the caller's process and start a successor on the same desk
stop_sessioneveryoneend the caller's process and its panel; the desk stays
parkLeaderevery running Worker writes its desk and stops, by a deadline
hireLeaderstart a Worker on a desk: a new name from the roster, or somebody who stopped, back on theirs
retireLeaderfile a stopped Worker's desk under archive/
permissionLeadersettle one rule for the whole instance, on a card you answer

restart_session and stop_session refuse until the desk was written since the event that asked, so the desk comes first, always. The reference has every argument.

The lifecycle

A session's context filling up, going idle, running out of quota and being parked are one flow each, and none of it is a phrase to recognise: the server sends a frame it set itself, and the session answers with a tool call.

Nothing is enforced at any context size: when a session restarts stays the session's own decision, and the event carries the size reached and all three sizes, so a session can see what it is counting toward. An event that asks nothing of a session does not cancel an ending the server is already waiting on: a seat told at 55 minutes to write its desk and stop is still ended at 60, whatever else it is told in between.

A seat on a turn — a permission stop included — is never idle. A stop keeps the desk and the panel's rows; anything addressed to the Leader starts it again, and hire on a stopped Worker's name brings it back on the same desk.

Quota

The server reads the usage windows Claude Code reports with every turn — the session window and the weekly one — and the weekly window of the one model that has its own, from the account's usage endpoint. Two threshold pairs in openovai.json cover them, quota: { "5h": [90, 95], "7d": [97, 99] } by default: a warning stage and a critical one for each. One event, quota-low, is sent at both stages and says which window and when it resets.

At the warning every running seat is told. A Worker writes its desk and stops; the Leader tells you — which window, that the Workers stopped, the reset time — writes its desk and stays, because talking to a warm Leader costs little. No Worker is hired from here until the window resets.

From the critical stage the server gates every turn: before anything goes on any stdin it checks the window, and a frame that would not pass waits in the server's queue rather than failing mid-work. A Worker still mid-turn is interrupted and told again, with interrupted="true": do not resume, write your desk and stop. The Leader is told once and not interrupted. A message to a held seat answers at once that it is held, and the page says which window and when it resets. After the reset, held frames are released the Leader's first, then the Workers', each in the order they arrived, and the Leader brings the Workers back on their desks. The one model's own window holds that model and nothing else: no process starts on it while it is spent, and every other model goes on.
