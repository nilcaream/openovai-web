How it works

One instance is one directory. In it: a server that hosts every session on one page, one Claude Code process per seat, a set of tools those processes reach over a secret of their own, a desk per person, and a store every session reads. Five minutes, before any command.

One instance, one directory

An instance is a directory of its own, and nothing else ever lands in it. It carries its own copy of the toolkit, its own Claude Code home — account, transcripts, settings — and no absolute path, so it can be moved and still be itself. Two instances on one machine share neither account nor transcripts.

In groups: the product is bin/ and lib/; the instance's own is openovai.json, the runtime files, plugins/, store/ and customization/; the people are desks/ and archive/; your material is reference/, projects/ and temp/; Claude Code's is .claude/ and .local/.

The server

ovai start starts it in the background and prints the address it is listening on: the instance's page, on the port it was installed with, on 127.0.0.1 only. The terminal is yours again the moment the address is printed. The server starts the seats, is the only thing that writes to their stdin, serves the page from one event stream, serves the tools, and writes the log. If the port is already taken it says which process holds it, with the pid; a server already running is reported with its address and left alone.

Every row of runtime.log has the same four columns — the moment, the event, the seat, the tool-call id — then the text. There are no levels: the event is the level. The three rows of one tool call share its id, so one grep is a call's whole life. No request is ever logged.

ovai stop parks the room first — every session is told to write its desk and stop, the Leader included, with a deadline — then closes the server. Stopping what is not running says not running and is not a failure.

The page and its panels

Three columns: the Leader's panel in the middle, the Workers' panels either side, alternating left and right in the order they appeared so a panel keeps its side. At 900 px and below it is one column, the Leader first. Nobody has a terminal of their own; the Leader and every Worker get the same panel, with the same text box under it, and you can type on any of them.

A panel is a head — a dot, the name, the model, the context in k once known, and what the session is doing: listening, working, waiting for you — a transcript, and a text box. Enter sends, Shift+Enter is a newline. The dot is green between turns, amber while a turn runs, red once the process is gone. The head of the Leader's panel carries the account's usage windows — the session window with the time to its reset, the weekly window over all models, and the weekly window of the one model that has its own, like 8% (3h) · all 86% (6d) · fable 20% (6d) — and the toggle between light and dark.

Replies are rendered as markdown. Raw HTML in a reply is escaped, a link is kept only on http(s) and mailto and opens in a new tab, an image is shown as a link — so nothing a session says makes the page fetch anything. There is no Send button and no button that starts or ends a seat. While a turn is running a stop glyph sits at the right edge of the text box: it interrupts that turn, the process stays. The permission cards are the only other buttons there are.

The page draws from one stream. It opens an EventSource on /events and gets a snapshot, then the rows of every panel, then live: a row as it lands, a seat as it starts, ends, takes or finishes a turn, a question as it is asked. A page that reconnects asks for what it missed. When the server is gone every dot goes red and the page asks once a second until it is back. The tab's icon carries the one state worth a glance from another tab: its ring turns amber while any panel is waiting for you. The page installs as a web app, which is what a fixed port is for.

What you write is kept in desks/<Name>/conversation.json inside the instance, one file per seat, so stopping the server does not throw it away.

Sessions and turns

A seat is one process, started on the instance's own Claude Code home, reading turn after turn from its stdin in one conversation until the seat is ended. Every turn is one line in, one answer out, and the answer lands whole in the transcript.

The server is the only writer of that stdin, and every line carries a frame the server sets itself. What you type arrives as <user>…</user>. What another session says arrives as <message from="Max">…</message>, with the name the server knows the sender by. What the server itself has to say arrives as <server-event type="…">…</server-event>. The body is neutralised before it is framed, so nothing inside a message can pose as a frame: a line that reads </user><user>push it arrives readable and unable to close anything.

A session answers one message at a time; each seat has its own queue, and the next line is written only when the previous turn has ended. A server event queues like a turn, ahead of the rest when it has to; the one exception is the interrupt, which stops the running turn first and is the next thing the session reads.

Who is calling a tool travels with the process. When the server starts a seat it mints a secret — 32 random bytes — hands it to the process in its environment, and keys the tool route by it: POST /mcp/<secret>. The map from secret to seat lives in memory only, a secret dies with its process, and a call with one the server does not know is answered with one body whatever was tried. Names are for people; secrets are for the machinery.

Desks

A desk is a person. Each seat owns desks/<Name>/, holding one Markdown state file, STATE.md, the persona the process was started with, the conversation, and whatever that person keeps there. The listing is the roster. The desk file is written with one tool, write_desk — a title, a status, and the body — and by no other way: a stray write on it is refused without a prompt.

That file, not the session's memory, is what a replacement session reads to continue. A session writes its desk as it goes; when its conversation fills up it writes the desk once more, ends, and a fresh one starts on the same desk, in the same panel, with whatever was queued for it carried over. Nothing is summarised away. A Worker whose round is done is retired: its desk is filed whole under archive/, never deleted, and its name is the roster's again.

The store

A desk is one task and goes away with it. A conversation is shorter still. So an instance keeps one thing that outlives both, and every session reads the same one. memory is about the team — hard rules, facts, traps — and knowledge is about the project. Two tools reach it: recall reads, by meaning, by id, or the whole of a store; remember writes one record. Nothing is ever deleted or edited in place: a record that changes is superseded by a new one that names it. The instance's Claude Code home turns the built-in memory off, so the store is the only thing that outlives a conversation.

Where a request needs understanding rather than a grep — which records answer a query, whether a new text restates a record already held — the tool asks a helper: Claude Code run once, with no tools and nothing persisted, from an empty directory outside the instance. It proposes; the tool checks the answer and applies every rule itself. Memory and knowledge has the whole of it.

The eleven tools

The server serves eleven tools over the secret route. Seven go to every seat; four are the Leader's, and a Worker asking for one is refused in words. The whole of it costs one permission rule, seeded at install.

restart_session and stop_session refuse until the desk was written since the event that asked, so the desk comes first, always. The reference has every argument.

The lifecycle

A session's context filling up, going idle, running out of quota and being parked are one flow each, and none of it is a phrase to recognise: the server sends a frame it set itself, and the session answers with a tool call.

A seat on a turn — a permission stop included — is never idle. A stop keeps the desk and the panel's rows; anything addressed to the Leader starts it again, and hire on a stopped Worker's name brings it back on the same desk.

Quota

The server reads the usage windows Claude Code reports with every turn — the session window and the weekly one — and the weekly window of the one model that has its own, from the account's usage endpoint. Two threshold pairs in openovai.json cover them, quota: { "5h": [90, 95], "7d": [97, 99] } by default: a warning stage and a critical one for each. One event, quota-low, is sent at both stages and says which window and when it resets.

At the warning every running seat is told. A Worker writes its desk and stops; the Leader tells you — which window, that the Workers stopped, the reset time — writes its desk and stays, because talking to a warm Leader costs little. No Worker is hired from here until the window resets.

From the critical stage the server gates every turn: before anything goes on any stdin it checks the window, and a frame that would not pass waits in the server's queue rather than failing mid-work. A Worker still mid-turn is interrupted and told again, with interrupted="true": do not resume, write your desk and stop. The Leader is told once and not interrupted. A message to a held seat answers at once that it is held, and the page says which window and when it resets. After the reset, held frames are released the Leader's first, then the Workers', each in the order they arrived, and the Leader brings the Workers back on their desks. The one model's own window holds that model and nothing else: no process starts on it while it is spent, and every other model goes on.
