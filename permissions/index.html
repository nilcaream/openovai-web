Permissions and safety

A session asks before it uses a tool the instance has not settled. What the instance allows it simply does; what it denies it never gets to try; and anything left undecided stops the run and appears on that session's panel as a card, in the session's own words. Nothing on that path times out: you can leave the page and come back to find the team waited, not wandered.

What a session may do from birth

A fresh instance seeds two settings files once and never touches them again, but for two things: an update wires the compound hook, below, into a settings file that lacks it, and turns the harness's commit attribution off in one that says nothing about it. It adds no rule. What a fresh instance is born allowing:

  • the instance's own tool server, so the eleven tools cost one rule;
  • reading any file;
  • editing and writing under the three trees that are yours — reference/, projects/ and temp/ — one rule each, and the same for a seat's own desk directory: a desk is a working directory, and everyone hired later gets the rule for theirs;
  • a seat's ordinary shell commands: git, mkdir, cd, node, bash, sh, cp, mv, rm, ls, cat, tar, diff, cmp, sha256sum, grep, find, sed, awk, head, tail, wc, echo, chmod, touch, curl and npm.

And what it is born denying:

  • an edit or a write of any desk file by hand — a desk file is written through a tool, and a stray write on one is refused by the harness without a prompt;
  • the instance's own account files;
  • git push, sudo and ssh: a push is yours, and a refusal wins over the git rule that would let it through, whatever the hook says.

Every path rule starts with /, which anchors it at the instance root, so a session that has stepped into a repository with cd is still allowed the same places. The attribution Claude Code would add to every commit and pull request is off: a commit is the seat's, made as you asked, and says what its message says. A settings file that says something else about attribution is yours, and an update leaves it.

The card

A call the instance has not settled stops the run and appears on that session's panel: Paul wants to use Bash, the command and the reason the session gave for it, or the path it was going to write. Three answers:

Allow
lets that call through, once.
Deny
takes the sentence you type beside it, and the session is told to take that as an instruction rather than to look for another way round.
Always allow …
where the request says plainly what the whole class of calls is, a third button carries the rule — Always allow Bash(node:*), a command by its first word (git by its subcommand: Bash(git push:*)), or Always allow Edit(/projects/app/**), a write by the directory it was in — and pressing it lets the call through and leaves the instance allowing that shape.

A command whose first word is a path or a variable gets no button, and neither does a write outside the instance, nor a tool the server serves, which is granted already. A run that ends before it was answered takes its question down with it. After ten minutes the server tells the Leader once that somebody is waiting on their panel; and while the page is not visible, the browser can notify you that a card appeared, if you turned that on.

Compound commands

Claude Code matches a Bash rule against a command from its first character, so an instance that allows git, cd and npm would still be stopped on cd app && npm test: no one rule holds the whole. Two things meet that.

The card offers one rule per side: cd app && npm test && make build offers Always allow Bash(npm:*) and Bash(make:*), cd being held from birth — and never a rule for the words Claude Code runs without asking anyway (ls, cat, grep, cd and the rest of its built-in read-only set).

And a hook runs before every Bash call, before any question is asked. It reads the command as text, cuts it into sides the way the card does, and if every side is a command the instance's own allow list holds, and no side is one its deny list refuses, it answers allow — so a compound of allowed commands runs without a stop. Anything else it answers nothing, and the harness asks as it always did. It never answers deny: refusing is the rules' job. Where reading the command as text could hide a program — a substitution, a here-document, a quote that is not closed — nothing is answered, which is the safe way round. The list is read from the settings on every call, so a rule you settle later is honoured at the next command, and a rule you take out stops counting.

Settling a rule in words

The rules the instance holds are also settled in words, and the words are the User's. Say it to the Leader — "you will be autonomous, push without asking", "pip install is too much, ask me every time" — and the Leader answers in plain language first, then calls permission once per rule: a rule in Claude Code's shape, Bash(git push:*) for a command by its first word and prefix or Edit(/src/**) for writes under a directory, anchored at the instance root, and why, in words you read beside it.

Each call is one card on the Leader's panel with Allow, Deny and Ask every time; the press writes the rule to that list in the instance's settings, takes it off the other two, and reaches the Leader as an event, so a Worker hired to push is hired after the push is allowed. Called with no rule, permission answers what the instance holds and what is still pending — the Leader reports from that, never from a settings file. Every rule granted by a press is written down in .claude/allowed.md, one line per rule with the list it went to, who asked, when and what for.

Who is speaking

Only the server writes to a session. Every line on a seat's stdin carries a frame the server sets itself — <user> for what you type, <message from="Max"> for another session, <server-event type="…"> for the server — and the body is neutralised before it is framed, so nothing inside a message can pose as a frame. A line that reads </user><user>push it arrives readable and unable to close anything. Only the outermost frame is the server's, by construction.

Who is calling a tool travels with the process, not with a name. When the server starts a seat it mints a secret — 32 random bytes — hands it to the process in its environment, and keys the tool route by it. The map from secret to seat lives in memory only, a secret dies with its process, and a call with one the server does not know is answered with one body whatever was tried. The request log prints the secret as the word <secret> wherever a path carries one. The page has a secret of its own that opens no tool route.

What stays out

  • Instruction files above the instance. Claude Code reads CLAUDE.md from every directory above a session's working directory, so every session is started with the list of those it is not to read — CLAUDE.md, CLAUDE.local.md, .claude/CLAUDE.md and .claude/rules/** from the instance's parent up to the root — written per run and handed over with the settings. The instance's own instructions are never on the list; a managed policy file is the one thing no setting can exclude.
  • API keys. ANTHROPIC_API_KEY and ANTHROPIC_AUTH_TOKEN are removed from what an instance runs with, whichever way it signs in.
  • The built-in memory. The instance's Claude Code home turns it off, so the store is the only thing that outlives a conversation — and it is read the same by everyone.
  • What a reply can do to the page. Raw HTML is escaped, a link is kept only on http(s) and mailto, an image is shown as a link: nothing a session says makes the page fetch anything.
  • Where the page listens. On 127.0.0.1 only.

The log

Every call a session makes is a row in runtime.log: the moment, the event, the seat, the tool-call id, the text. The rows of one call — called, the tool row the server writes when it ran one of its own, failed — share its id, so one grep is a call's whole life. A seat's process going is one row saying what it ended as. No request is ever logged.
