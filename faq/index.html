FAQ and troubleshooting

The questions a first evening raises. Most of them have one answer, and the answer is usually something the instance already said — on the panel, in the terminal, or in runtime.log at the root.

The Leader is not answering

The Leader starts on the first thing addressed to it, so a panel that shows history and no reply is usually an instance that is not signed in. ovai configuration reports whether the instance has a credential, and says plainly that it has not checked it against Anthropic: finding out costs a request, so the first message is where a dead credential shows up. Under --auth login, ~/workspace/bin/ovai login opens a browser once. Under --auth inherit the instance takes CLAUDE_CODE_OAUTH_TOKEN from the environment it was started in — start the server from a shell that has it. The seat's own words for what went wrong are on its panel; the server's are in runtime.log.

The port is taken

ovai start says so and names what holds it — the pid, and the command line when it can read one — and asks you to stop that. A server of this instance already running is a different message: it is reported with its address and left alone. If the port is somebody else's for good, install over the instance with --force and another --port, or 0 for whatever is free; the option you give is written into openovai.json and everything else is kept.

ovai update refuses

It refuses while the server is running, and while any session of this instance is running — found on the machine by the Claude Code home it carries. Each one is named with the kill <pid> line that ends it, and the process's command line after it as a comment, so a session of yours can be told from a process that merely carried the instance's home; the line still pastes. ovai stop first parks the room properly — every session writes its desk — and then the update goes through. It also refuses to go backwards by name: --downgrade takes an older release anyway, and --from <url or directory> takes one from somewhere other than GitHub.

A Worker went quiet, said "back in a moment", or disappeared

Three different things. Quiet: the Leader is told about a silent Worker at 10 and at 50 minutes; at 55 any seat is told it goes cold at 60, writes its desk and stops. A seat on a turn — a card waiting included — is never idle. Back in a moment: its context passed the ceiling; it wrote its desk and restarted, and a successor is starting on the same desk, in the same panel, with whatever was queued carried over. Disappeared: a Worker whose process has gone is dimmed with its text box closed and removed from the page thirty seconds later; the desk stays, and the Leader's hire on that name brings it back on the same desk with its rows. Ask the Leader; it was told each time.

Everything stopped at once

Two causes, told apart by what the panels say. If a panel says which usage window is spent and when it resets, it is the quota gate at its second stage: the server holds every turn until the window resets, then releases them, the Leader's first; nothing is lost, and nothing to do but wait, or talk to the Leader, whose held turns say so. The Workers stopped a little earlier, at the first stage, on their own; after the reset the Leader brings them back with hire.

If instead every instance on the machine stopped with the same message, an inherited token expired: under --auth inherit the token is long-lived but not forever and cannot refresh itself. Mint a new one with claude setup-token, export it where the instances are started from, and start them again; one token fixes them all.

A session was waiting on me and I did not see it

Nothing on that path times out: the run waits for as long as you take, and after ten minutes the Leader is told once that somebody is waiting on their panel. To be told yourself, turn the exclamation-mark switch on the Leader's head on: a card appearing on any panel then reaches you through the browser's notifications while the page is not visible, and a click on it brings that panel into view. From another tab, the page's icon carries a ring while any panel is waiting for you. Both are described under notifications.

Can I run two instances?

Yes; that is what an instance being a directory is for. Two on one machine share the runtimes under ~/.local/share/openovai/ and nothing else: not the account, not the transcripts, not the port — each has its own Claude Code home. For two different accounts install both with --auth login and sign each in; with --auth inherit they share the one token. Give them different ports, or 0 each.

Where is the conversation?

What you see on a panel is kept in desks/<Name>/conversation.json inside the instance, one file per seat, so stopping the server does not throw it away; the desk file beside it is the state the next session starts from. Claude Code's own transcripts are under .local/ at the instance root, its config directory for this instance. A retired Worker's directory is moved whole under archive/, conversation included.

Can it run on macOS?

The requirement is a Linux desktop; that is what it is built and run on, and nothing else is claimed. The pieces are ordinary — a POSIX shell script, Node.js, Claude Code, a page on 127.0.0.1 — but the pinned runtimes are fetched for Linux, and no other platform has been measured. When one has, this page will say so.

Is it safe to leave running?

The page listens on 127.0.0.1 only. A session does what the instance allows, never gets to try what it denies — git push, sudo and ssh from birth — and stops on a card for anything undecided, for as long as you take. A seat idle for an hour writes its desk and stops. A tool of the server's is one permission rule; a tool of yours under plugins/ is one you wrote. The permissions page has the seeded rules and the shape of the ones you add; what you leave the room allowed to do is what it can do while you are away.
